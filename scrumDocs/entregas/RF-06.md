## 1. Qué quedó implementado

La interfaz de RF-01, reescrita como aplicación React + TypeScript construida con
Vite, con el mismo comportamiento, los mismos textos, los mismos tiempos y los
mismos ids del DOM. Además quedó sentada la estructura de monorepo del proyecto.

Estructura:

```
/
├── frontend/          Vite + React + TypeScript  ← nuevo (esta tarjeta)
│   ├── src/
│   │   ├── components/    ChatHeader, MessageList, MessageBubble,
│   │   │                  OptionsBar, ChatForm
│   │   ├── hooks/         useChat (la máquina de estado del chat)
│   │   ├── lib/           routing.ts (los 4 casos, función pura),
│   │   │                  texts.ts (literales), time.ts, welcome.tsx
│   │   ├── styles/        tokens.css (variables de docs/style.md),
│   │   │                  chat.css (el resto, portado verbatim)
│   │   └── __tests__/     rf-06.test.tsx (8 tests)
├── backend/           Django  ← NO incluido; se crea en la tarjeta de RF-02
├── docs/              guías (style.md, arquitectura)
└── scrumDocs/         metodología (autogenerada, no se toca a mano)
```

Qué hace, igual que RF-01:

- Al montar: indicador de escritura, y a los 500 ms el saludo con markup
  (`👋 <strong>¡Hola! Bienvenid@ a Profesionales</strong><br>…`) + los dos botones.
- Click en **Iniciar Sesión** / **Registrarse**: mensaje del usuario,
  respuesta del asistente a los 600 ms, botones retirados.
- Texto libre: se muestra, se vacía el campo, y a los 700 ms enruta los 4 casos
  (saludo, login, registro, genérico). Los casos login/registro disparan el flujo
  idéntico a presionar el botón, incluido su mensaje (igual que app.js).

**El XSS se resuelve solo:** React escapa `{texto}` por defecto, así que el texto
del usuario nunca es HTML. No hay sanitize manual que mantener. El único markup
es `WELCOME_CONTENT`, un literal propio del repo.

**Sin StrictMode a propósito** (`frontend/src/main.tsx`): el flujo de bienvenida
corre por timers y el doble-montaje de StrictMode duplicaría el saludo. Está
anotado en el código.

## 2. Cómo se levanta y cómo se prueba

Requisitos: **node >= 20**. Red la primera vez para `npm install`.

```bash
# 1. dependencias (una sola vez)
cd frontend && npm install

# 2. compilación con chequeo de tipos (condición 9, primera mitad)
cd frontend && npm run build

# 3. suite de las 8 condiciones (condición 9, segunda mitad + condición 10)
cd frontend && npm test

# 4. servidor de desarrollo (queda en :5173)
cd frontend && npm run dev
#   y abrí http://localhost:5173

# 5. recorrido integrado de punta a punta, en un solo comando
bash scrumDocs/entregas/RF-06.sh

# 6. recorrido integrado + 200 corridas midiendo latencia
bash scrumDocs/entregas/RF-06.sh --carga 200
```

`RF-06.sh` compila, sirve `frontend/dist/` él solo (elige puerto si el 3000 está
ocupado), chequea `GET /` y los assets compilados, corre `npm test`, y sale con
código distinto de 0 si algo no pasa. Lo mata al servidor al terminar.

## 7. Qué quedó afuera / qué se asumió

**Quedó afuera** (otras tarjetas):

- Backend Django y login/registro reales → RF-02 y RF-03. No hay `backend/`
  todavía; se crea en la tarjeta de RF-02.
- Pruebas en navegador real: la suite corre sobre **jsdom** (vía Vitest), que
  ejecuta el DOM pero no pinta píxeles. El criterio 8 se verifica leyendo las
  hojas de estilo fuente.
- Accesibilidad con lector de pantalla y dispositivo real: no medidos.

**Supuestos / decisiones que conviene revisar:**

1. **Los archivos viejos quedan intactos** (`index.html`, `app.js`, `styles.css`
   en la raíz), por decisión explícita. RF-01 está en `in_production` y su test
   de humo en la app pide `GET /styles.css` y `GET /app.js`; sacarlos rompería
   ese test. Se sacan cuando la versión React quede promovida, actualizando el
   manifest en ese momento.
2. **`package.json` de la raíz no se toca.** `frontend/` es un proyecto Vite
   independiente, tal como piden las condiciones (`cd frontend && …`).
3. **TypeScript estricto, configuración del template oficial** (`tsc -b` en el
   build). El único ajuste fue agregar `"node"` a `types` para los tests.
4. **No se cargaron Tests en la app todavía** porque la tarjeta sigue en
   `to_do` y no hay rama de la app. Se cargan (desarrollo en Aprobado,
   integración en Pendiente) cuando exista la rama y el `checkoutCommand`.
5. **`scrumDocs/scrum-manifest.json` no se tocó** por la misma razón: la entrada
   de RF-06 se crea cuando el `POST /github/branch` devuelva su rama.
6. **Nada de esto es una métrica de rendimiento en navegador real.** Los únicos
   números medidos son los del §5 (build ~1 s; suite 8/8 en ~9 s) y los tiempos
   de respuesta del asistente, cronometrados en la suite (≤ 3000 ms bienvenida,
   ≤ 2000 ms clics).
7. **CORS:** igual que en RF-01, `python -m http.server` no manda
   `Access-Control-Allow-Origin`. No se arregló acá por la misma razón: es ajuste
   de entorno, no de esta tarjeta, y hay Requerimientos operacionales (RO-01) que
   lo cubren. `RF-06.sh` y `npm test` corren locales y no dependen de CORS.
