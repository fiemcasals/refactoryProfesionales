## 1. Qué quedó implementado

Una interfaz estática (HTML + CSS + JS, sin backend) que deja al usuario en la
pantalla de bienvenida con un asistente de chat y la ruta ya marcada hacia login
o registro.

Al cargar la raíz se ve:

- Cabecera con la marca **Profesionales** y el estado **Asistente en línea**.
- Mensaje de bienvenida del asistente (`¡Hola! Bienvenid@ a Profesionales…`).
- El chat listo: `#messages-list`, `#options-container`, `#chat-input`, `#chat-form`.
- **Exactamente dos** botones: `Iniciar Sesión` (`#btn-login`) y `Registrarse`
  (`#btn-register`), ambos `type="button"`. No hay selector de opción numérica
  ni campo de texto obligatorio para elegir.

Interacciones:

| Acción | Resultado |
|---|---|
| Click en **Iniciar Sesión** | mensaje del usuario `Quiero iniciar sesión`, respuesta del asistente en < 2 s, botones retirados del DOM |
| Click en **Registrarse** | mensaje del usuario `Quiero registrarme`, respuesta del asistente en < 2 s, botones retirados del DOM |
| Texto `hola` / `¿cómo estás?` | mensaje de bienvenida/estado + **repone** los dos botones |
| Texto `login` / `acceder` | dispara el flujo de inicio de sesión (mismo resultado que el botón) |
| Texto `registro` / `registrarme` | dispara el flujo de registro |
| Cualquier otro texto | mensaje genérico *«Por favor selecciona una de las opciones»* + repone los dos botones |

En todos los casos el campo `#chat-input` queda vacío después de enviar.

**Corrección incluida (criterio 7 — XSS):** `appendMessage()` usaba
`bubbleDiv.innerHTML = text`. El texto tecleado por el usuario llegaba a la
pantalla como markup, así que `<img src=x onerror=…>` o `<script>` entraban al
DOM. Ahora el mensaje del usuario se escribe con `textContent` y el `innerHTML`
queda reservado para los literales propios del archivo (el `<strong>`/`<br>` del
saludo). Ver `app.js`, función `appendMessage()`.

## 2. Cómo se levanta y cómo se prueba

Requisitos: **node >= 20**, **python3** (sólo para servir), y red la primera vez
para `npm install`.

```bash
# 1. dependencias de la suite (una sola vez)
npm install

# 2. suite de las 8 condiciones de aprobación
npm test

# 3. servidor local (queda en :3000 si ese puerto está libre)
python3 -m http.server 3000
#   y abrí http://localhost:3000

# 4. recorrido integrado de punta a punta, en un solo comando
bash scrumDocs/entregas/RF-01.sh

# 5. recorrido integrado + 200 corridas midiendo latencia
bash scrumDocs/entregas/RF-01.sh --carga 200

# 6. forzar un puerto concreto
bash scrumDocs/entregas/RF-01.sh --base http://localhost:8099
```

`RF-01.sh` hace todo solo:

- Elige el puerto: usa el 3000 si está libre **o si ya está sirviendo esta app**;
  si lo ocupa otro proceso, baja al 3001, 3002, … hasta 3005.
  *(En esta máquina el 3000 lo tiene `mora-app`, un Next.js de otro proyecto,
  así que en la práctica corre en el 3001.)*
- Levanta el servidor él solo si nadie lo está sirviendo, y lo mata al terminar.
- Chequea `GET /`, `/styles.css`, `/app.js`, los 5 ids clave del HTML y la suite.
- Sale con código distinto de 0 si algo no pasa.

## 7. Qué quedó afuera / qué se asumió

**Quedó afuera** (pertenece a otros requerimientos, no a RF-01):

- Login y registro reales: validación contra API, sesión, `localStorage`.
  → RF-02 y RF-03, que todavía están en `to_do` y **no están implementados**.
- Responsividad de la app en sí; el criterio 48 px se cumple, pero no hubo
  pruebas en dispositivo real ni con lector de pantalla.
- Automatización en navegador real (Chrome/Playwright): la suite corre sobre
  **jsdom**, que ejecuta el JS y el DOM pero no pinta píxeles ni mide estilo
  computado. El criterio 8 se verifica leyendo la hoja de estilos.
- Cualquier test de endpoint que existía antes: el usuario borró los Tests de la
  app antes de arrancar; esta entrega crea los suyos de vuelta (ver §8).

**Supuestos / decisiones que tomé y conviene revisar:**

1. **Se agregó `package.json` + `jsdom` como única dependencia.** El repo no
   tenía ni `package.json` ni suite de tests en ninguna rama, así que no había
   framework que reutilizar y tampoco un comando que correr. Sin esto no había
   forma de que las 8 condiciones queden automatizadas y en verde.
2. **`tests/` es nuevo en la rama** y `.gitignore` sólo ignora `node_modules/`.
3. **`scrumDocs/` no existía en esta rama** (existía sólo en `dev`); se creó
   `scrumDocs/entregas/`. No debería conflictuar al mergear.
4. **`docs/scrum-manifest.json` de esta rama trae `baseUrl`
   `http://10.24.206.203:8080`** (una IP de red local, contradice
   `http://localhost:3000` de `qa-sync`) **y `testIds` que apuntan a Tests ya
   borrados de la app.** No lo toqué hasta que se decida cómo resolverlo.
5. **`docs/tests-manifest.json` de esta rama tiene 6 tests, 5 de ellos ajenos a
   RF-01** (RF-02/03/04/05/RNF-01) y **ninguno con `description`**, que es campo
   obligatorio según `qa-sync`. Tampoco lo toqué por la misma razón.
6. **La app no tiene webhook de GitHub** en esta rama (existe sólo en `dev`:
   `.github/workflows/kanban-sync.yml`), así que el tablero se mueve por los
   `PATCH` de la API y no por mis pushes.
7. **CORS:** `python -m http.server` no manda
   `Access-Control-Allow-Origin`. Si QA quiere correr "Verificación en vivo" desde
   la app de Scrum contra un servidor local, el navegador le va a bloquear la
   lectura de la respuesta. No lo arreglé acá por dos razones: es un ajuste de
   entorno, no de RF-01, y este proyecto todavía no tiene ningún Requerimiento
   operacional que lo cubra — meterlo de contrabando en esta tarjeta sería
   exactamente lo que el flujo prohíbe. **Si QA necesita el entorno verificable
   desde la app, hay que abrir una tarjeta para CORS** (sólo el origen de la
   instancia, sólo en settings de desarrollo). Mientras tanto, `RF-01.sh` y
   `npm test` corren locales y no dependen de CORS.
8. **Nada de esto es una métrica de rendimiento**: no medí tiempos de render en
   navegador real ni accesibilidad con lector de pantalla. Los únicos números
   medidos son los del §5 (suite 8/8; carga 50/50 `200`, 2 ms promedio, 22 ms
   peor) y los tiempos de respuesta del asistente, que sí están cronometrados en
   la suite (≤ 3000 ms bienvenida, ≤ 2000 ms clics).
